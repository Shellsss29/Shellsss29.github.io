Training Large Models When You Don't Have a Fancy GPU

How I fit a 7B parameter model on my 16GB GPU (and you can too)

Shailly Bhati CS Grad Student | Probably Debugging Right Now

The Problem (That Ruined My Weekend)

So last week I was trying to fine-tune a 7B parameter model for my research project. Wrote my training script, hit run, grabbed some coffee... and came back to this:

RuntimeError: CUDA out of memory.
Tried to allocate 2.00 GiB (GPU 0; 15.78 GiB total capacity)

Great.

My GPU has 16GB of memory. The model needs... way more than that. I spent the next 4 hours going down the rabbit hole of "how do people even train these things?" and honestly, it's a mess out there. Everyone says "just use cloud GPUs!" but I'm a grad student, not Google. I can't drop $5/hour on compute.

So I figured it out the hard way. Here's what actually worked.

First, Let's Talk About Why This Happens

Okay so when you're training a model, GPU memory goes to a bunch of different things. I didn't realize this until I actually looked into it, but the model weights are actually the SMALLEST part of what you're storing.

Here's where the memory actually goes for a 7B parameter model:

Model Weights: 28 GB
(7 billion parameters × 4 bytes each in FP32)

Gradients: Another 28 GB
(Because you need gradients for every single parameter during backprop)

Optimizer States: 56 GB
(If you're using Adam - which everyone does - it keeps momentum and variance for each parameter. That's 2× the model size!)

Activations: 15-30 GB
(All the intermediate outputs from each layer that you need for backprop)

Total: Around 130 GB for FP32 training 😭

So yeah, my 16GB GPU didn't stand a chance.

The thing is, most tutorials don't tell you this stuff. They just say "here's how to train a transformer" and assume you have infinite memory. But after trying like 10 different things, I found a combination of techniques that actually work.

Solution 1: Mixed Precision Training (This One's a Game Changer)

Okay so this was the first thing I tried and honestly it's kind of magic.

The idea: Instead of using 32-bit floats (FP32) for everything, use 16-bit floats (FP16) for most of it.

What I got:

  • 50% less memory (went from 8.2GB to 4.5GB in my tests)
  • Training was actually FASTER (like 20-30% faster)
  • Accuracy stayed basically the same

I was skeptical at first because "lower precision = worse results" right? But modern GPUs (anything with Tensor Cores) are actually OPTIMIZED for FP16. It's wild.

Here's How I Did It

PyTorch has this thing called Automatic Mixed Precision (AMP). It's stupid easy to use:

from torch.cuda.amp import autocast, GradScaler

model = MyModel().cuda()
optimizer = torch.optim.Adam(model.parameters(), lr=1e-4)
scaler = GradScaler()  # This is the magic part

for batch in dataloader:
    optimizer.zero_grad()

    # Forward pass in FP16
    with autocast():
        outputs = model(inputs)
        loss = criterion(outputs, targets)

    # Backward pass with scaling
    scaler.scale(loss).backward()
    scaler.step(optimizer)
    scaler.update()

That's literally it. Three extra lines and you get 2× memory reduction + faster training.

The GradScaler thing is there because FP16 has a smaller range than FP32, so tiny gradients can become zero (underflow). The scaler multiplies them before backprop, then unscales before the optimizer step. Prevents underflow without sacrificing precision where it matters.

Real talk: This should be your default. There's basically no downside unless you're doing something really weird.

Solution 2: Gradient Checkpointing (When FP16 Isn't Enough)

So even with FP16, I was still running out of memory. Turns out activations (those intermediate layer outputs) were eating up a ton of space.

The idea: Instead of storing ALL activations during forward pass, only store some of them. Recompute the rest during backprop.

Yeah, it's slower. About 10-20% slower in my tests. But honestly? If it's the difference between training working vs. crashing, I'll take it.

How It Works

import torch.utils.checkpoint as checkpoint

class MyModel(nn.Module):
    def __init__(self):
        super().__init__()
        self.layer1 = TransformerBlock()
        self.layer2 = TransformerBlock()
        self.layer3 = TransformerBlock()
        self.layer4 = TransformerBlock()

    def forward(self, x):
        # Checkpoint expensive layers
        x = checkpoint.checkpoint(self.layer1, x)
        x = checkpoint.checkpoint(self.layer2, x)
        x = checkpoint.checkpoint(self.layer3, x)
        x = self.layer4(x)  # Don't checkpoint everything
        return x

You don't have to checkpoint every layer. I found checkpointing every 2-3 layers is a good balance. Still get good memory savings without making training crawl.

When to use it: If FP16 alone isn't cutting it. Which for me, it wasn't.

Solution 3: 8-bit Optimizers (Because Why Not)

This one's newer and honestly kind of feels like cheating.

Remember how Adam optimizer stores momentum and variance? That's 2× your model size in FP32. With 8-bit optimizers, you quantize those states down to 8-bit ints.

Memory saved: About 30-40% of optimizer memory
Accuracy impact: Basically none in my tests
Speed impact: Maybe 5% slower? Barely noticeable

Implementation

Using the bitsandbytes library (which you'll need to install separately):

import bitsandbytes as bnb

# Instead of regular Adam:
# optimizer = torch.optim.Adam(model.parameters(), lr=1e-4)

# Use this:
optimizer = bnb.optim.Adam8bit(model.parameters(), lr=1e-4)

One line change. That's it. 4× reduction in optimizer memory footprint.

I was honestly surprised this worked so well. Expected some accuracy drop but got basically nothing.

My Results (On an RTX 4090)

I tested this on ResNet-50 with CIFAR-100 to see how much memory I could actually save:

What I Used GPU Memory Speed Accuracy
Baseline (FP32) 8.2 GB 100% (baseline) 78.5%
+ FP16 4.5 GB 122% (faster!) 78.4%
+ Checkpointing 3.1 GB 114% 78.4%
+ 8-bit Optimizer 2.6 GB 109% 78.3%
What this means:
  • Went from 8.2GB down to 2.6GB (3.2× reduction)
  • FP16 actually made it FASTER
  • Lost like 0.2% accuracy total (basically nothing)
  • Now it fits on way cheaper GPUs

For my 7B parameter model, this meant I could actually train it on a single consumer GPU instead of needing to rent cloud compute.

Some Other Tricks I Learned

1. Gradient Accumulation

If you're still running out of memory, reduce batch size and use gradient accumulation:

accumulation_steps = 4  # Simulate 4× larger batch

for i, batch in enumerate(dataloader):
    with autocast():
        loss = model(batch) / accumulation_steps

    scaler.scale(loss).backward()

    # Only update every N steps
    if (i + 1) % accumulation_steps == 0:
        scaler.step(optimizer)
        scaler.update()
        optimizer.zero_grad()

2. Monitor Your Memory

# Check what's actually using memory
allocated = torch.cuda.memory_allocated() / 1e9
peak = torch.cuda.max_memory_allocated() / 1e9
print(f"Using {allocated:.2f}GB, peaked at {peak:.2f}GB")

Final Thoughts

Look, I'm not a systems person. I just wanted to train a model and my GPU kept crashing. These techniques got me unstuck.

The main takeaway: you don't need fancy hardware to train modern models. With FP16 + checkpointing + 8-bit optimizers, I went from needing 100GB+ to fitting everything in 16GB. That's accessible hardware.

Is it as fast as training on 8× A100s? No. But it's way better than not training at all.

If you're a student or researcher without access to massive compute, try these techniques. They actually work.
